# An embedding host's plugin SDK exposes flowi types directly; no prefix aliasing

## Status

accepted

## Context

flowi was extracted from an embedding host, which migrated back onto flowi and translated its
internal codebase to flowi's `fl_*`/`Fl*` vocabulary (no duplication, no translation layer). The
open question was the host's **plugin SDK**: plugins are separately-compiled `.so`s authored
against stable headers, including third-party plugins. Those headers were uniformly named with the
host's own legacy prefix, and many of the types are flowi-owned (the legacy string type alone was
~430 refs across the SDK headers).

Two ways to keep the SDK working once the host's internals are `Fl*`:

- **Alias every flowi-owned type back to a host-prefixed name** so authors see a uniform SDK
  (generated by a new api_gen prefix-export mode).
- **Expose the flowi types directly** as `Fl*`, and keep the host prefix only for genuinely
  host-specific types (the service vtables, the core-plugin types, app-domain types).

The aliasing's only benefit is cosmetic prefix uniformity. Its cost is real: a new api_gen
alias-export mode, an emitter that needs `typedef` (type names) **plus** `#define` (enum variants
like `FlThemeSlot_InteractiveBase` and the `FL_*` convenience macros, neither of which a `typedef`
carries), and ongoing scope decisions. Crucially, the downstream `.so` ABI coupling to flowi's
struct layouts (ADR-0043) **exists either way** — aliasing only *hides* the coupling, giving a
false sense of independence. flowi is an acknowledged dependency of the host, not a secret.

## Decision

The host's plugin SDK **uses flowi types directly** (`Fl*`) for everything flowi owns, and reserves
its own prefix for host-specific types only. The SDK is deliberately **mixed-prefix**: `Fl*` signals
the toolkit/foundation layer, the host prefix signals the host/app layer. Prefix-by-provenance is a
standard C convention and is self-documenting; a one-line SDK note ("`Fl*` types come from the
flowi UI toolkit; the host-prefixed types are host APIs") covers authors who don't know what flowi
is.

No prefix aliasing is built. flowi gains no downstream-specific export capability.

## Considered alternatives

- **api_gen generic prefix-alias export** (emit host-prefixed aliases of `Fl*` for a selected subset, driven
  by the host's build). Rejected: substantial machinery (CLI/mode, `typedef`+`#define` emitter, enum
  variant + macro aliasing, output routing) for purely cosmetic uniformity; and it hides — does not
  remove — the layout ABI coupling. Kept on file as the escape hatch **if** a hard branding
  requirement to make flowi invisible appears later; at that point this ADR would be superseded and
  the export mode designed (the open points: subset-selection spec, function aliases in/out,
  flat-vs-per-module output).
- **Hand-written alias shim.** Rejected for the same cosmetic-only benefit plus silent drift.

## Consequences

- A future reader seeing `Fl*` types inside the host's own-prefixed plugin headers (e.g. a core-load
  entry point taking the host's service-API pointer, a `FlString`, and the host's core-info pointer)
  should understand this is **deliberate**, not an un-wrapped leak to "fix."
- The plugin ABI layout constraint (ADR-0043) stands on its own and is now the primary reason to be
  careful with flowi's exported struct layouts.
- Bringing flowi's plugin-facing-but-hand-written APIs (`jobsys`, `json`, `log`, `perf_scope`) under
  the IDL was not a prerequisite for the SDK (nothing needs alias-generation); it was a separate
  codegen-consistency cleanup and has since been done (`api/core/jobs.def`, `json.def`, `log.def`,
  `perf_scope.def`).
