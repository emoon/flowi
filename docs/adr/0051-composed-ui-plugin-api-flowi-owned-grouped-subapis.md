# The composed UI plugin API is flowi-owned and grouped into per-domain sub-APIs

## Status

Superseded by ADR-0058: the composed UI plugin vtable (`FlUiApi`/`g_fl_ui`, `plugin_root`) was removed and
plugins now call the exported direct `fl_*` API. Originally accepted (amends ADR-0032: reverses its *ownership*
and *flat-shape* choices for the composed UI
vtable, while preserving its core "indirection only at a dynamic boundary" principle; builds on
ADR-0046 service-vtable codegen, ADR-0035 "api_gen owns the public surface", ADR-0043 frozen layouts)

## Context

ADR-0032 settled that flowi calls its own UI direct (`fl_button(...)`) and that the **composed
plugin vtable** — the table a separately-compiled `.so` plugin drives the UI through — is **owned and
generated by the host** as **one flat ~100-slot UI API struct**, with flowi running
api_gen only for its own `direct` surface. ADR-0046 then carved out flowi-owned *foundation-service*
vtables (`FlArenaApi`/`g_fl_arena`) for the dlopen'd C++ cores, and built the per-domain
`EmitStyle::PluginVtable` emitter that arena uses today.

Two consumers needed to build their UI *from plugins*: an existing embedding host (plugins called a
flat vtable) and a second, new application. Revisiting ADR-0032's two incidental choices against
that need:

- **Ownership (host vs flowi).** If the plugin surface is flowi's, every app embedding flowi exposes
  the *same* surface, so the same plugins load and the same UI code is reused across apps. That
  portability is the point of a shared toolkit ABI, and it is lost when each host owns (and can drift)
  its own plugin vtable.
- **Shape (flat vs grouped).** A single flat ~100-slot table has no seams: it is fragile to evolve
  and any change ripples across the whole surface. Grouping the surface into one vtable **per UI
  domain**, behind a small root table of pointers, gives each domain an independent append-only seam.

ADR-0032's *core* reasoning — a vtable's indirection is only worth paying at a real dynamic boundary,
never for in-process calls — is untouched by either change: the grouped vtable lives **only** at the
plugin boundary; flowi-internal and in-process Rust callers keep the direct `fl_*` API.

## Decision

**flowi owns and generates the composed UI plugin API, shaped as a root table of per-domain
sub-API vtables.**

- **Shape.** A root `FlUiApi`/`g_fl_ui` holds one pointer per UI domain to that domain's **sub-API**
  vtable (`FlPainterApi`, `FlLayoutApi`, `FlButtonApi`, …). A plugin calls
  `g_fl_ui->painter->draw_quad(...)`. Each sub-API is the *same* table shape ADR-0046's service
  emitter already produces, but reached through the root — **no standalone `g_fl_painter` global**.
  Granularity is **one sub-API per `.def` domain**; no coarse multi-domain bundles.

- **Ownership & distribution.** flowi generates the surface into `flowi/include/flowi/service/`
  (`service/ui.h`). Consumers **do not run api_gen** — they `#include` the generated header the same
  way a core includes `service/arena.h`. There is one naming (`Fl`/`fl`); ADR-0032's host-side
  host-prefix profile/codegen step is dropped.

- **Membership & order authored in one place.** A new top-level IDL construct,
  `plugin_root Ui { version = N; painter; layout; button; … }`, is the **single source** of which
  domains compose the root and **in what pointer order**. Being listed emits that domain's sub-API
  vtable (slots pointing at the domain's direct `fl_*` bodies) plus its root pointer, in list order.
  The surface is an explicitly-controlled, **append-only** ABI: new domain → append a line (tail
  pointer); new call → append a slot at a sub-API's tail. An older plugin safely ignores either tail.

- **Membership is additive, not a mode-switch.** Unlike `#[attributes(service)]` (which *replaces*
  the direct emit — Rust off, no direct `fl_*`, vtable only), a `plugin_root` member keeps **all** its
  existing outputs — direct `fl_*` C functions (internal callers) and the Rust façade (in-process
  `rust/flowi`) — and *additionally* emits its sub-API slot. A UI domain therefore emits three things
  (direct C + Rust façade + plugin slot); a standalone foundation service emits one.

- **One root version.** `FL_UI_API_VERSION` (the `version` field of `plugin_root`), bumped on *any*
  additive change, negotiated once at `fl_init_ui_api(get, pd)`. All sub-APIs ship together in one
  flowi build, so there is no per-sub-API version; the append-only rule is what guarantees a bump is
  backward-compatible.

- **Foundation services unchanged.** Standalone foundation-service vtables (ADR-0046; arena today,
  string/log later per-demand) stay standalone — their own `g_fl_<svc>` injected as a sibling of UI
  in the host registry — **not** members of the `Ui` root. A core needs arena without needing the UI.
  This effort is **UI-only**; no new foundation services are added here.

- **ADR-0032's core principle stands.** Internal/in-process callers use direct `fl_*`; the
  indirection exists only at the plugin boundary.

## Considered Options

- **Keep ADR-0032 as-is (host-owned flat UI API struct).** Rejected: host ownership forfeits
  cross-app plugin portability, and the flat 100-slot table is the fragile-to-evolve shape grouping
  exists to fix. The vendored copy / per-host drift surface also persists.
- **Per-sub-API version numbers.** Rejected: all sub-APIs ship in one flowi build, so an "old
  painter + new layout" mix can't occur; N constants + N negotiation checks solve a non-problem.
  Independent *evolution* is delivered by the grouped append-only layout, not by independent version
  numbers.
- **Auto-synthesize the root from per-def `service(ui)` tags (membership = file-discovery order).**
  Rejected: a frozen append-only ABI must not have its slot order be an emergent property of the
  filesystem. The explicit `plugin_root` list makes order a reviewed diff in one place.
- **Coarse functional groups (`widgets` = button+checkbox+slider…).** Rejected: needs a
  cross-def aggregation map and emitter work, and collapses the independent per-domain append seam
  that motivates grouping in the first place. One-per-`.def` reuses the existing emitter verbatim.
- **Reuse the old ADR-0030 `g_fl_ui->domain->fn` composed-root scaffolding.** The vestigial
  api_parser comments describe that killed shape; the new root is rebuilt fresh (flat list of
  sub-API pointers), not revived from it.

## Consequences

- ADR-0032 is amended: its single-source-IDL and direct-internal-call principles stand and
  strengthen; its claims that the composed UI vtable is *host-owned* and *one flat table* are
  withdrawn. The host's own-prefix `plugin_vtable` profile is no longer needed for the UI.
- api_gen gains: the `plugin_root` top-level construct (parser + grammar), a root-composer emitter
  (root struct + `g_fl_ui` + `fl_ui_get_public_api` adapter + `fl_init_ui_api`/version glue), and the
  rule that a member emits *additively* on top of its direct + Rust outputs. The per-domain sub-API
  vtable body reuses ADR-0046's existing `PluginVtable` emit.
- The generated `service/ui.h` must pull in the headers of every type its slots cross by value
  (`Signal`, `WidgetConfig`, `ImageHandle`, `FlString`, …); those layouts are the frozen plugin data
  ABI of ADR-0043, reached via the ADR-0035 `mod`/`extern opaque` type-closure rules. No render IR or
  internal-only type enters the IDL.
- CONTEXT.md gains **Composed UI API** and **Sub-API**; the **Service API vtable** term is amended to
  note services are standalone (not root members) and that the host no longer owns the composed UI
  vtable.
- The plugin surface is now versioned and frozen by flowi, independently of any one host, and grows
  only by appending — domains to the root, slots to a sub-API.
