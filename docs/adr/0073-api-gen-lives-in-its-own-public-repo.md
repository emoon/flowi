# api_gen lives in its own public repo and is consumed as a library

Status: accepted. Partly superseded: `flowi-core` and `flowi-vfs` were folded back into this repository (`rust/flowi_core`,
`rust/flowi_vfs`), so they are no longer separate consumers of the generator. The generator itself stays in
[emoon/api-gen](https://github.com/emoon/api-gen).

`api_gen` sat in `rust/tools/api_gen/`, with flowi's 87 `.def` files inside the tool's own
directory at `rust/tools/api_gen/api/`. Four projects already used it, and three of them
reached into a flowi checkout by filesystem path: another downstream tool via
`../flowi/rust/tools/api_gen` (with a `FLOWI_API_GEN` override), the embedding host via
`$FLOWI_DIR`, and flowi itself in-tree.

That is workable while every consumer is private. It stops working as flowi's `core` and
`vfs` become the public `flowi-core` and `flowi-vfs` repositories: their public headers are
api_gen output, so a contributor without a flowi checkout could not regenerate them, and
those repositories could not run the regenerate-and-compare gate flowi's CI has. The cost is
already visible in another downstream tool, whose CI runs no such check because it cannot reach the
generator — its committed headers carry an em dash where current api_gen emits a hyphen, so
they were produced by an older generator and have since drifted.

The generator is not flowi-specific. Naming prefixes, include root and prefix, export stem
and the `use` lines emitted into generated Rust are all configuration; two unrelated
vocabularies already drive it. `api.pest` also records that this
generator was itself "forked from flowi_core's api_gen" — it has drifted by forking once
already.

## Decision

**api_gen moves to [emoon/api-gen](https://github.com/emoon/api-gen), public and MIT, and
consumers call it as a library rather than shelling out to it.**

- **The `.def` files are consumer content and do not travel with the tool.** flowi's moved
  from inside the tool directory to `api/` at the repo root.
- **flowi consumes it from `codegen/`, a dev-only crate in its own workspace.** api_gen's
  dependency tree therefore never reaches the `Cargo.lock` of the shipped `flowi_sys` and
  `flowi` crates, and `codegen/Cargo.toml` pins the exact generator commit (`rev`) that
  produced the committed output. Bumping the generator means changing `rev`, running
  `cargo regen`, and committing the updated `codegen/Cargo.lock` with the regenerated output.
- **`cargo regen` regenerates; `cargo regen-check` is the gate.** Both are aliases in
  `.cargo/config.toml`. `scripts/gen_bindings.sh` and
  `scripts/gen_service_wrapper_bindings.sh` are deleted; both targets are entries in
  `codegen/src/lib.rs`, so one command covers all of flowi's committed codegen.
- **The gate compares instead of diffing the worktree.** It regenerates into a temp
  directory and compares against the committed files, so it never mutates the tree, it works
  on a dirty tree, and it reports which file drifted. Staleness is keyed on the
  `@generated by api_gen` stamp, because `flowi/exports/` holds hand-maintained files
  (`flowi_handwritten.txt` and its siblings) beside generated ones.
- **The banner names the command that regenerates it.** `c_gen.rs` and `rust_gen.rs`
  hardcoded `Regenerate with scripts/gen_bindings.sh` into every generated C and Rust file,
  ignoring `Config::gen_script`, which only the marshalling emitters honoured. All emitters
  now honour it; flowi sets it to `cargo regen`.
- **`generate` returns `Result<Summary, Error>` and prints nothing.** `Error` covers the
  filesystem and a `Config` asking for an output without the settings that output needs. A
  malformed `.def` still panics with a diagnostic: that is an input bug to fix, not a
  condition a caller handles. `Config` and `Naming` derive `Default`, so a caller names only
  the outputs it wants.

## Consequences

- Regenerating needs a Rust toolchain, including in the C-only consumers. That was already
  true — the old scripts ran `cargo run`.
- A one-time diff rewrote the banner line of 220 committed generated files here, and will do
  the same in another downstream tool and the embedding host when they adopt the pattern. No other
  line changed.
- ADR-0030, ADR-0033 and ADR-0044 refer to `gen_bindings.sh`; read those references as
  `cargo regen`.
- Another downstream tool and the embedding host still shell out to a flowi checkout. They each need
  their own `codegen/` crate; until then their generated surfaces stay ungated.
